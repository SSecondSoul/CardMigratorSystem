# Vue/San 批次验证问题报告

## 目标

把一次 Vue/San 批次的人工检查过程整理为可追溯、可计算、适合论文引用的 `.ipynb`。报告既要记录已解决问题，也要保留证据边界、残余风险和可复现的检查代码。

默认输出目录：

```text
notebooks/01-data-exploration/
```

优先使用包含日期与批次标识的文件名，例如：

```text
YYYY-MM-DD_vue_san_<batch-id>_validation_issues.ipynb
```

同一批次已有报告时，先判断用户是要求更新还是新建版本；不要静默覆盖历史实验记录。

## 职责边界

- 本 skill 负责读取证据、汇总问题、计算统计并创建或更新报告 notebook。
- 除非用户明确要求，不修改组件源码、生成脚本、数据集元数据或人工测试页面。
- 不承担 `manual-runner-config` 的逐组件页面切换，也不承担 `vue-san-dataset-production` 的组件生产。
- 不启动服务器、浏览器或 Jupyter UI，除非用户另行要求。

## 证据要求

不要只依赖概括性聊天记忆。按实际存在情况读取：

1. 用户在当前验证流程中报告的现象和明确确认；
2. 批次设计矩阵、组件清单和复杂度元数据；
3. 受影响的 Vue/San 最终源码；
4. `git status`、`git diff` 或仍可追溯的生成脚本；
5. `migration_notes.json`、既有 notebook 和验证日志。

若证据不足：

- 不推断未出现的问题，不把猜测写成根因；
- 将无法确认的结论标为“推测”“仅静态核对”或“未复核”；
- 只有用户明确确认过，才能写“人工确认通过”；
- 若缺失信息会改变批次范围、缺陷率或结论，再向用户询问。

需要建立或读取结构化问题记录、确定统计口径时，阅读 [references/validation-evidence-schema.md](references/validation-evidence-schema.md)。

## 问题分类

必须区分以下类别，不能全部计入同一个缺陷率：

- `production_defect`：批量生产完成后，首次人工检查发现的组件缺陷；
- `repair_regression`：修复已有问题时新引入的缺陷；
- `expected_behavior`：符合业务规则但容易被误认为异常的行为；
- `remaining_risk`：尚未工程化解决的流程、证据或可复现性风险。

对每条问题记录组件、框架范围、现象、触发操作、根因、修复、改动文件、验证方式和当前状态。一个根因造成多个紧密相关的表象时通常记为一条；同一组件存在不同根因时分别记录。

## 工作流程

### 1. 确定批次范围

- 从用户指定的设计矩阵或 manifest 获取组件顺序与复杂度。
- 核对 Vue/San 文件是否存在。
- 记录计划组件数、实际检查数和明确确认数，不默认三者相等。

### 2. 重建问题清单

- 按人工检查顺序整理现象与修复。
- 对照最终源码确认修复确实存在。
- 若生成脚本存在，检查最终源码与生成源是否漂移，以及重新生成是否会覆盖补丁。
- 将框架运行时问题、共享布局问题和测试环境问题分开。

### 3. 计算可审计指标

至少按证据允许的范围计算：

- 组件对总数与复杂度分布；
- 人工检查覆盖率；
- `production_defect` 条数；
- 受影响组件数及比例；
- 受影响组件的复杂度与框架分布；
- 根因分布；
- 修复后的明确复核数量与比例。

所有比例都写出分子、分母。修复回归、预期行为和残余风险单独报告，不纳入生产缺陷率。

### 4. 编写 notebook

根据批次事实调整结构，通常包括：

1. 标题、日期、批次与证据声明；
2. 组件清单和验证方法；
3. 问题总览表；
4. 可执行的统计单元格；
5. 根因分析与可复用修复模式；
6. 对最终源码的静态核对单元格；
7. 验证结果与可报告指标；
8. 当前残余风险和后续行动；
9. 论文可用结论与有效性威胁；
10. 相关文件索引。

使用合法的 notebook JSON 结构。新建代码单元格时设 `execution_count` 为 `null`、`outputs` 为空数组；代码优先只依赖 Python 标准库，并从当前目录向父目录查找项目根目录，避免 notebook 只能在单一 cwd 下运行。

### 5. 保持研究表述严谨

- “静态检查通过”“代码单元可执行”“人工确认通过”“自动化测试通过”是不同证据等级。
- 只报告当前批次的观察结果，不把小样本比例外推为一般缺陷率。
- 同时记录样本选择、人工判断、环境与测试覆盖造成的有效性威胁。
- 保留不成功的修复尝试或中间回归，因为它们能够反映迁移与验证成本。

## 验证

完成 notebook 后至少执行：

- 用 JSON 解析器重新读取文件，确认 `nbformat`、`cells`、唯一 cell id 和基本字段合法；
- 编译代码单元格；如果代码只做只读检查，则执行并确认断言通过；
- 检查报告引用的关键路径存在；
- 复算正文中的数量与比例，避免分子、分母或分类口径不一致；
- 用差异或状态检查确认只修改了用户要求的报告文件。

若没有运行 notebook UI，应明确说明验证的是 JSON 和代码单元，而不是可视化渲染。

## 完成汇报

向用户提供 notebook 的可点击路径，并简要报告：

- 批次规模；
- 问题与受影响组件数量；
- notebook 结构和代码单元验证结果；
- 是否还修改了其他文件。
