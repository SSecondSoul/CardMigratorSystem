# 原生 Ref 依赖互操作协议 v1：待审核设计稿

日期：2026-11-14。状态：**DRAFT / 未批准 / 未实现 / 不可用于生产放行**。

本文件是下一轮离线可行性实验的提案，不是已经实现的 API、迁移规则、正式实验协议或新的通过证据。用户本轮授权为设计与核对；没有授权接入生产、引入新的部署依赖或改变公开输入范围。

## 1. 已有证据与问题

基线为 `data/experiments/analysis/formal_30_v4_native_ref_structure_v13_20261114/`，SHA-256 清单应先校验。

- 原 Ref 矩阵：192点、4个差异，来自对象属性和数组元素对象属性的写入；新结构矩阵：116点、2个差异，来自 Vue.set 新属性后的普通写入。这两组分开报告，不能当作6个正式组件失败。
- 结构变化已能接入固定原生观察器的 `dep`，但每个响应式属性的 `dep` 封装在 `defineReactive` 闭包内，结构依赖不能替代它。
- 原116、扩展152、描述符104、路径172点保持一致。原扩展清理矩阵另有1个生命周期错误通道差异，未解决。
- 原生 Ref 传入原生 San 子组件后的计算值／真实绑定／渲染缓存传播仍未证明；不能用既有不含该输入的36点父子回归替代。
- 上一轮205项测试包含已知反例的复现检查，不意味着所有输入已等价。本设计没有新增运行时测试或改变上述数量。

冻结 Vue2.7.16 源码定位：`data/experiments/manual_followups/task_manager_async_scope_v7_prepared_20261113/vendor/vue-2.7.16.js` 中的 `defineReactive`、`dependArray`、`Watcher.prototype.get/cleanupDeps/update`、`doWatch` 与 `effect`。静态定位及指纹在本设计证据包的 `source_anchors.json` 中复算。

## 2. 目标与不做事项

目标：让输入提供方显式提供原生依赖能力，使迁移端在原有队列时机获取通知，不改变 Ref、内部对象、原型或业务方法行为。

不做事项：

- 不直接写全局 Dep.target，不补丁框架原型，不重写原生属性 getter/setter，不加第二套观察器，不复制／代理／轮询输入。
- 不把结构 dep、__v_isRef、__ob__ 或看似正确的 dep 方法形状当作能力授权或等价证明。
- 不把 Vue watch/effect 藏在 San 组件或测试设备里替迁移实现观察。若研究输入端的公开 Vue 订阅 API，必须明确归属于输入提供方、披露运行时依赖并另获离线实验批准。
- 不让 provider 执行业务 watcher、保存、统计或生命周期回调；不缩减原公开 key/value 契约以改高通过率。
- 不移除现有生产诊断，不改人工验收页面或现有应用错误配置，不开展正式独立测试。

## 3. 三方职责

| 角色 | 负责 | 不负责 |
| --- | --- | --- |
| 输入提供方 provider | 识别其实际管理的输入；按协议收集原生依赖、递交通知、清理订阅；声明并验证运行时与调度能力 | 执行 San 或源组件的业务回调、复制输入、决定生产通过 |
| 迁移端 consumer | 提供源匹配的只读遍历；维护原队列顺序／去重／取消；调用已迁移业务回调；处理同身份值的缓存失效 | 挖取私有属性闭包 dep、偷偷加载 Vue、推断 provider 的纯度 |
| 宿主应用与独立门禁 | 显式注册可信 provider 和适用域；绑定版本／源码／证据；校验未知域及伪造通过 | 仅凭 JSON 声明、人工通过、标记名或测试总数直接豁免诊断 |

输入方可继续持有 Vue 管理的真实 Ref；这与完全不含 Vue 的独立 San 部署是不同架构。后者需要单独证明输入构造的迁移，不能用本协议偷偷保留 Vue 依赖。是否采用哪种部署架构尚未批准。

能力应由宿主显式注册，按原输入引用／所有权域匹配，例如应用持有的 WeakMap 注册表；不得往 Ref 上塞标记或接受模型生成代码自己声明的 provider。注册不是安全沙箱，可信实现和读取副作用仍需专项证据。

## 4. 概念接口：仅规格，不是可调用实现

以下名称用于约定职责，不暗示 Vue 已提供同名 API：

```text
provider.describe(inputIdentity, requestedProfile) -> capability | unsupported
provider.open(ownerToken, rowToken, ownerGeneration, onInvalidate, onFault) -> session
session.capture(captureEpoch, sourceMatchedRead) -> receipt
session.dispose() -> void
```

- describe 不得为探测而触发业务 getter、改输入、安装订阅；返回支持域和版本指纹，不返回“生产已通过”。
- open 在受审宿主中创建 owner/row 专属会话；无初始业务回调。首版不支持运行中热切换 provider。
- capture 同步调用受控 sourceMatchedRead，收集其实际触及的原生依赖。只读不等于访问器无副作用；读取顺序／次数必须与源 oracle 比较，未知访问器不能被声明覆盖。
- receipt 仅含不透明依赖／会话标识、版本和清理状态，不传原生 Watcher／Dep 对象给迁移端，不用序列化对象快照替代身份。
- onInvalidate 只递交失效事实和 owner/row/当前有效订阅标识，不读写业务状态、不执行回调、不自行重收集；consumer 保持原队列行为。
- onFault 携带发生阶段和原错误，不承担吞错／改错／业务降级；错误通道与执行时机必须另证。
- dispose 幂等，只释放此 owner/row 的份额。晚到通知不能复活已销毁 owner，另一 owner 的共享输入订阅必须仍有效。

这是新接口草案，不保证仅靠 Vue2.7 公开 API 可以实现。实现不出来必须保留阻断，而不是转用内部 API 后继续称其为公开实现。

## 5. 必须保持的通知与收集时序

```text
初始源匹配读取并建立依赖
  -> 原生写入同步产生失效通知
  -> consumer 将对应原队列项标记为 pending（不立即运行）
  -> 在源匹配的实际 dispatch 位置重新收集／清理依赖
  -> 运行该项原业务回调
  -> 后续通知使用新依赖集
```

1. 原生写入到 onInvalidate 的相对同步时机必须匹配，不可简单换成 Vue.nextTick、Promise 或防抖。
2. 不得每次失效就提前遍历和清理；旧别名在首次 flush 前仍可能合法通知，实际重收集后才移除旧订阅。
3. ownerGeneration 只标识拥有者生命周期／明确重新绑定，不因一次 Ref 替换就递增并丢弃旧订阅通知；captureEpoch 与生存期代际分开。
4. 去重、项间顺序、回调内写入、重入、销毁前取消均依源队列，而不是 provider 自带的默认批处理策略。
5. 一次读取同时经过普通迁移状态与原生 Ref 时，consumer 私有token收集与 provider 原生收集必须覆盖同一源匹配读取，不额外遍历两遍。
6. 同一 owner/row 的原生域只能由一个方案负责；V12/V13 私有 dep 实验订阅不能与新 provider 并行订阅同一依赖。去重不得掩盖重复安装或泄漏。
7. 新订阅的安装、旧订阅的释放以及读取异常时的部分收集状态都须有源对照。Vue Watcher.get 将清理放在 finally 中，但其中的深遍历也可能先抛错，不能假定后续清理总会完成，更不能未经验证就把异常一律定义为“回滚全部”或“一律提交”。

## 6. 对象身份与子组件传播

- Ref 与 value 的引用不变，不因协议需要生成替身、深拷贝或 __ob__ 装饰。
- 数组下标、长度、Vue.set/delete、普通新属性、getter-only、shallowRef 与已有观察值严格区分，沿用源差异；provider 不得擅自让全部写入变成响应式。
- 原生值传给子组件时，同身份不等于未变化。必须定义局部失效版本如何关联已绑定值，并在真实框架绑定路径上验证 computed／DOM／副作用。
- 禁止把测试手工调用 child.data.set 或改模板当成真实父子绑定传播的证明；旧36／56点只作为回归控制。
- 新增属性后的再次写入、删除后旧别名、数组元素替换、Ref 替换都要验证订阅更新；不能只测一次“变更后界面更新”。

## 7. 异常、清理与应用配置

原 V7 应用配置仅批准浏览器、无源祖先错误捕获、全局仅报告的受限调查。它不是本依赖 provider 的批准，也没有证明新回调纯度。

新草案将依赖能力与错误回调声明分开：依赖收集必然读取受控响应状态，不能冒用原错误处理器 `no-reactive-reads-or-writes` 的声明。错误处理器限制不因新增 provider 自动放宽。

必须区分初始化／探测失败、同步赋值失败、capture 失败、异步业务回调失败、订阅清理失败和生命周期失败。在哪个通道报告、是否抛回调用方、何时仍运行后续项由源证据决定。

- 宿主没有 provider 或 profile 不支持：在实验候选准入时明确阻断并报告未实现域，不能返回成功、跳过输入或回填通过。这不代表原公开契约被合法缩小。
- 会话建立阶段失败不得留下半安装订阅；运行中失败必须按受审源策略处理，不以 fail-closed 为名改变业务可观察行为。
- 销毁取消与 beforeDestroy/detached 的先后需单独核对；不能提前清空订阅来隐藏既有生命周期序列化错误。
- 订阅计数、通知来源及移除后的残余回调要分别记录；“没有活跃回调”不等于已经证明所有暂存对象的 GC 行为。

## 8. 可行性路线与明确不采用的捷径

| 路线 | 本稿结论 | 下一步条件 |
| --- | --- | --- |
| 输入提供方使用受审公开 Vue 订阅 API | 候选路线，不是已证明方案；San 组件不调用 Vue | 先验证是否能满足 capture 时机、异常、旧别名和双调度器约束；单独批准离线原型 |
| 继续扩展结构 dep 订阅 | 不能解决私有属性依赖；只保留V13研究证据 | 不以其覆盖缺失属性域，不直接部署 |
| 私有 Watcher/内部 effect、直接改 Dep.target 或框架原型 | 本稿不授权 | 不得以公开 API 名义实施；如改变研究约束必须重新申请并单列版本 |
| 假设完全独立 San 部署，直接丢弃 Vue 输入互操作 | 不能推导为原公开接口等价 | 需要独立的应用级输入构造迁移设计，不自动缩小实验值域 |

静态源码核对发现：

- doWatch 的 flush=sync 路径将 update 指向 run，run 会调用 get 并重收集，可能早于原 consumer dispatch；不能直接当作协议实现。
- pre/post 路径走 Vue 队列，不自动等同于现有 San/Promise 队列的相对顺序。
- 开发构建中的 onTrack/onTrigger 不足以证明拟部署构建或调度语义支持，不能只靠调试事件放行。
- 冻结文件虽然导出了 Vue.effect，其旁注明确为 Vue2 内部测试用途；本稿不将它当作稳定公开 API。

以上是基于源码的候选风险判断，不是一次新运行时失败／通过结论。公开 API 不能满足时应停止该路线并提交设计决策，不能静默降级。
